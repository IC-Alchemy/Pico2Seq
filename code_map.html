There is no main(). Pico2Seq is an Arduino sketch on a dual-core RP2350: the 24-line Pico2Seq.ino only wires Core 0 (setup()/loop() → Application — everything except audio) and Core 1 (setup1()/loop1() → AudioEngine — audio synthesis only). All real logic lives in modules under src/.

CoreEntry pointOwnsHard rule
Core 0 controlsetup()/loop() → Application::begin()/update()uClock ISR (staging only), clock-event drain, step playback, touch matrix + tiles, TMAG5273/VL53L1X sensors, encoders, OLED + LED refresh, voice editor, session save/load~1 kHz pass; keep it snappy — USB serial and flash writes stall it

Cross-core communication is lock-free only: volatile/std::atomic flags (voicesReady, PPQN counter) and SpscQueues (per-voice control updates, the step ring, the heartbeat). No mutexes anywhere.

Input → sound, across the two cores

The same flow in words

Life of a step (Core 0, once per musical step)

  1. Stock uClock fires its alarm on core 0. The ISR callback onStepCallback (ClockService.cpp:26) does one thing: push the step number into a SpscQueue ring (drops + counts on overflow). Nothing else lives in ISR context.
  2. Application::update() (Application.cpp:169) drains the ring via ClockService::processClockEvents() (ClockService.cpp:61).
  3. Each drained step goes to StepPlayback::processSequencerStep() (StepPlayback.cpp:113) → Sequencer::advanceStep() (Sequencer.cpp:206) reads the current value of each of the 9 parameter lanes (each lane can have its own step count — polymetric).
  4. Values pass through VoiceEdit::composeLane (VoiceEditParameters.cpp:984) — sequencer tracks store ±0.5 offsets around each voice's base patch parameters — producing a VoiceState.
  5. updateActiveVoiceState() (StepPlayback.cpp:73) writes gates/notes into VoiceSystem, and Voice::updateParameters() (Voice.cpp:962) pushes the new parameters into that voice's SPSC control queue. Failed pushes are retried next pass by VoiceManager::flushControlUpdates().

Life of a sample (Core 1, continuously at 48 kHz)

  1. loop1() calls AudioEngine::renderNextBuffer() (AudioEngine.cpp:164), which blocks on a free DMA buffer — that blocking is the pacing.
  2. VoiceManager::processBlock() (VoiceManager.cpp:361) renders each voice: Voice::processBlock() (Voice.cpp:339) first drains one queued control update per sample, then renderSpan_ (Voice.cpp:364) runs the per-voice DSP chain from src/rpdsp/ (osc bank / waveguide / recipe / hypersaw / noise-FX → ladder or SVF filter → ADSR → overdrive/wavefolder).
  3. The mix goes through AudioSamples::toPcm16() (Pcm16.h:13) into the I2S DMA ring. Meanwhile the master gain ramps smoothly via VoiceManager::advanceMasterGain_().

Questions this map answers

Where is main()?

There isn't one. Arduino's dual-core lifecycle starts in Pico2Seq.ino: setup()/loop() (core 0) → Application::begin()/update(); setup1()/loop1() (core 1) → AudioEngine::begin()/renderNextBuffer().

Where is processBlock and who calls it?

loop1() → AudioEngine::renderNextBuffer() (AudioEngine.cpp:164) → VoiceManager::processBlock() (VoiceManager.cpp:361) → Voice::processBlock() (Voice.cpp:339) for each of the 4 voices. VoiceManager::processAllVoices() (:390) is the one-sample-at-a-time wrapper kept alive mainly by the host tests.

How do sequencer values become sound?

Sequencer::playbackValue() returns a stored ±0.5 modulation offset; VoiceEdit::composeLane (VoiceEditParameters.cpp:984) composes it around the voice's base patch parameters into a VoiceState; Voice::updateParameters() queues it; Voice::processBlock() applies it on the next rendered span. Note lane is an additive transpose around baseNote, not a replacement.

Where did MIDI go?

USB MIDI was removed 2026-09-06. src/midi/ is dormant plumbing with stub sends; nothing transmits. Gate/note bookkeeping for voices 0–1 still lives in MidiNoteManager as internal state only.

Which files can I unit-test?

Anything with no hardware dependency: all of src/pico2seq-core/, src/ui/ControlSurfaceLogic.cpp, most of src/voice/, the header-only AlchemyProto.h/TileButton.h, audio.cpp/sample_conversion.h (via stubs), FreezeWatchdog.h, plus the two header-only exceptions Pcm16.h and AppState.h's calibration. Keep new logic out of the src/app/*.cpp glue files — extract it into ControlSurfaceLogic or pico2seq-core instead.

Where are gates handled?

All four voices have software gates and duration timers in VoiceSystem, ticked by ClockService::processPendingGateTicks() (ClockService.cpp:83) on core 0. Voices 0–1 additionally get MidiNoteManager internal note tracking. The audio-side ADSR release tail lives on core 1 inside Voice.

Why does the Gate track matter specially?

The Gate lane's step count defines the whole pattern length for a voice; every other lane modulo-wraps against the global uClock step independently. That is what makes polymeter ("Note: 16, Filter: 8") work.

What do I run after changing code?

cmake -B build_test -DCMAKE_BUILD_TYPE=Debug && cmake --build build_test --parallel && ./build_test/tests/pico2seq_tests — plus the other three targets. There is no CI; the suite is the gate. Firmware builds need Arduino IDE / scripts/build_pico2seq.ps1 and a board.
